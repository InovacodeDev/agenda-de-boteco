# PostHog 2.2 — Reverse Proxy, CSP, Source Maps, Crash Nativo e Identidade Web — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fazer todo stack trace de produção apontar para o TypeScript original, sem perda por adblocker, e manter sessão/pessoa coerentes no PostHog web.

**Architecture:** Os eventos web passam a sair por `/<basePath>/ingest`, um rewrite em cada `next.config.ts`, então a CSP só precisa de `'self'`. Source maps web sobem no build da Vercel via `@posthog/nextjs-config`. No mobile, o Metro e o config plugin **já vêm no `posthog-react-native` instalado** (`posthog-react-native/metro`, `posthog-react-native/expo`), e o upload de Hermes, dSYM e mapping roda **dentro do EAS Build**, não no `deploy.yml` (que dispara `eas build --no-wait`). Identidade web vira um helper do core usado pelos 3 apps com login.

**Tech Stack:** Next.js 16 (`rewrites`, `skipTrailingSlashRedirect`), `posthog-js@1.425.1` (`api_host`, `ui_host`), `posthog-react-native@4.66.3` (`/metro` `getPostHogExpoConfig`, `/expo` config plugin), EAS Build (environment variables).

**Spec:** `docs/analise-2-posthog-proativo-erros.md` — Plano de Ação 2.2. **Depende do plano 2.1** (`reportException`, `buildPostHogNativeOptions`, `PostHogBrowserConfig.basePath`).

## Review Focus

1. **Multi-zone da landing** — o browser em `agendadeboteco…/client/ingest/…` passa pelo rewrite da `landing/vercel.json` até o deploy do client, e só então pelo rewrite do client até o PostHog. Validar em preview que `/client/ingest/decide` responde 200, e não 404 nem redirect com barra final.
2. **Request sem `NEXT_PUBLIC_POSTHOG_HOST`** (dev/CI): `rewrites()` devolve `[]` em vez de gerar destino `undefined/...` e quebrar o build. Coberto em Task 1 Step 3.
3. **CSP nova de web-client/web-artists bloqueando algo que funciona hoje** — ViaCEP (`https://viacep.com.br`, `services/cep.ts`), preview `blob:` do `ImageDrop`, imagens do Supabase Storage, fontes `next/font`. Coberto em Task 2 Step 3 (roteiro manual).
4. **Logout em outra aba ou expiração de sessão** — `resetAnalytics()` precisa disparar pelo evento de auth, não só pelo botão "Sair". O helper escuta `onAuthUserChange`. Teste em Task 5.
5. **Build EAS sem credencial de upload** (fork, dev local): o build deve passar com aviso, sem falhar. Coberto em Task 4 Step 4.

**Interfaces:**
- Produces (core): `export function postHogUiHost(ingestHost: string | undefined): string | undefined` — `https://us.i.posthog.com` → `https://us.posthog.com`, `https://eu.i.posthog.com` → `https://eu.posthog.com`; outro host (proxy próprio) → `undefined`.
- Em cada `next.config.ts`, inline e com docblock do porquê (o `next.config` não importa `@agenda/core`, cujo index puxa React; são 5 cópias de 8 linhas):
  ```ts
  const POSTHOG_INGEST = (process.env.NEXT_PUBLIC_POSTHOG_HOST ?? '').replace(/\/+$/, '');
  const POSTHOG_ASSETS = POSTHOG_INGEST.replace('://us.i.', '://us-assets.i.').replace('://eu.i.', '://eu-assets.i.');
  // config:
  skipTrailingSlashRedirect: true,
  async rewrites() {
    if (!POSTHOG_INGEST) return [];
    return [
      { source: '/ingest/static/:path*', destination: `${POSTHOG_ASSETS}/static/:path*` },
      { source: '/ingest/:path*', destination: `${POSTHOG_INGEST}/:path*` },
    ];
  },
  ```
  O `basePath` é aplicado pelo Next no `source`. Por isso o endpoint fica `/client/ingest/...`.
- Providers: `apiHost: \`${basePath}/ingest\`` (landing: `'/ingest'`), `uiHost: postHogUiHost(process.env.NEXT_PUBLIC_POSTHOG_HOST)`.

### Task 5: Identidade unificada nos apps web com login

**Files:**
- Create: `packages/core/src/services/analytics-identity.ts`; Test: `packages/core/src/services/analytics-identity.test.ts`; Modify: `packages/core/src/index.ts`
- Modify: `apps/web/hooks/useAppSync.ts` (novo `useEffect`), `apps/web-client/app/providers.tsx` e `apps/admin/app/providers.tsx` (`AppSyncBridge`)

**Interfaces:**
- Consumes: `onAuthUserChange` (`services/auth.ts`), `getCurrentUserExternalId` (`services/establishment-owner.ts`), `identifyAnalyticsUser`, `resetAnalytics`.
- Produces: `export function subscribeAnalyticsIdentity(initialUserId: string | null): () => void`. Mesma lógica de `apps/mobile-client/app/_layout.tsx:58-75`: login, ou troca para um id diferente, chama `getCurrentUserExternalId()` → `identifyAnalyticsUser(externalId)` quando não-nulo, com falha engolida, sem `console`. Usuário indo de não-nulo para `null` → `resetAnalytics()`. Identifica por `external_id`, nunca por `auth.uid()`. Chamado com `useAuthStore.getState().user?.id ?? null`.

Com o usuário persistido no boot, `initialUserId` já vem preenchido, e o primeiro evento de `onAuthUserChange` com o mesmo id não identificaria. Por isso o helper também identifica uma vez na assinatura quando `initialUserId !== null`.

Os 3 apps só ganham `useEffect(() => subscribeAnalyticsIdentity(useAuthStore.getState().user?.id ?? null), [])`. Os `identifyAnalyticsUser` já existentes nos `login/page.tsx` ficam: são idempotentes. `mobile` e `mobile-client` **não** migram neste plano (edição cirúrgica). Fica como sugestão de follow-up.

  - callback `{ id: 'u2' }` → `identify('ext-2')`.
