# PostHog 2.3 — Degradação Silenciosa, Saúde de Dados e Alertas Proativos — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Detectar no minuto em que acontecem registro corrompido no banco, fila offline travada, Realtime caído e regressão por release, sem derrubar a tela do usuário.

**Architecture:** As listas deixam de dar `.parse()` no array inteiro. Um helper do core mapeia linha a linha, descarta só a linha inválida e reporta `zod-schema-drift` com fingerprint estável. Paginação continua calculada sobre as linhas cruas. Services fora do padrão passam por `handleServiceError`, e com isso pelo `reportException` de 2.1. A fila de favoritos ganha teto de tentativas e descarte de erro permanente. O Realtime emite `realtime_degraded` com throttle. Super properties identificam app, versão, canal e plataforma em todo evento.

**Tech Stack:** Zod 3.23.8, Zustand 5 (`useFavoritesStore`), Supabase Realtime, `posthog-js`/`posthog-react-native` `register`, `expo-constants`.

**Spec:** `docs/analise-2-posthog-proativo-erros.md` — Plano de Ação 2.3. **Depende do plano 2.1** (`reportException`, `SafeErrorMetadata`, `toReportableError`, `PostHogBrowserClient.register`, `PostHogNativeClient.register`).

## Global Constraints

- Tudo de 2.1 vale aqui (AGENTS.md, zero-PII, CHANGELOG por commit, gate `pnpm typecheck && pnpm lint && pnpm test`).
- Fingerprint de drift: exatamente `['zod-schema-drift', <table>, <issuePath>]`. `issuePath` vem do primeiro issue, com índice numérico trocado por `*` e segmentos unidos por `.`. Nunca valor de campo.
- `recordId` só recebe identificador opaco: `external_id` quando a linha tem, senão `id` uuid. Em `musician_leads` nunca vai nome/telefone/instagram.
- Nenhuma dependência nova. Session replay mobile (`posthog-react-native-session-replay`) **não** entra aqui: exige aprovação separada.

## Review Focus

1. **Página cheia com a última linha corrompida** — `nextCursor` precisa vir da última linha **crua**, e `hasMore` do tamanho cru. Senão a paginação termina cedo ou repete a linha ruim para sempre. Testes em Task 1 para `listEvents` e `listMusicianLeads`.
2. **Todas as linhas inválidas** — a tela recebe `[]` (vazio, não erro), e um `$exception` sai por linha até o teto `MAX_DRIFT_REPORTS_PER_CALL = 3` por chamada, para não estourar quota num feed inteiro corrompido. Teste em Task 1.
3. **Erro não-Zod dentro do mapper** (ex.: `TypeError` por campo `null` inesperado) — não pode ser engolido como drift: propaga para o `catch` do service. Teste em Task 1.
4. **Favorito pendente para alvo apagado (FK `23503`) ou bloqueado por RLS (`42501`)** — sai da fila na primeira tentativa e é reportado. Erro transitório (rede) fica até `MAX_PENDING_OP_ATTEMPTS = 5`. Teste em Task 2.
5. **Canal Realtime oscilando `CHANNEL_ERROR`/`SUBSCRIBED` a cada segundo** — no máximo um `realtime_degraded` a cada `REALTIME_DEGRADED_THROTTLE_MS = 300_000` por canal. Teste com fake timers em Task 3.

### Task 1: Validação item a item com reporte de drift

**Files:**
- Create: `packages/core/src/utils/schema-drift.ts`; Test: `packages/core/src/utils/schema-drift.test.ts`
- Modify: `packages/core/src/queries/catalog.ts:245,266,326,364,417,463,471,498` (as 8 chamadas `.map(mapX)` de listagem); `packages/core/src/services/proximity.ts:157`; `packages/core/src/services/musician-leads.ts:111`
- Test: `packages/core/src/queries/catalog.byIds.test.ts` (ou um `catalog.drift.test.ts` novo ao lado), `packages/core/src/services/proximity.test.ts`, `packages/core/src/services/musician-leads.test.ts`

**Interfaces:**
- Consumes: `reportException` (2.1).
- Produces:
  ```ts
  export const MAX_DRIFT_REPORTS_PER_CALL = 3;
  export function mapRowsLenient<Row, Item>(
    rows: readonly Row[],
    map: (row: Row) => Item,
    options: { table: string; idOf: (row: Row) => string | undefined },
  ): Item[];
  ```
  Só `ZodError` é capturado por linha: `reportException(error, { fingerprint: ['zod-schema-drift', table, issuePath], recordId: idOf(row) })`. Qualquer outro erro é relançado.

Aplicação:
- `catalog.ts`: `const rows = (data ?? []) as EventRow[]; const items = mapRowsLenient(rows, mapEvent, { table: 'events', idOf: (r) => r.external_id ?? r.id });` e o cursor passa a usar `rows.at(-1)` e `rows.length < limit`. Mesmo padrão para `establishments`, `music_styles` (`idOf: r => r.id`), `cities`, `notifications`.
- `proximity.ts:157`: `mapRowsLenient(rows, (r) => nearbyEstablishmentSchema.parse(mapRow(r)), { table: 'nearby_establishments', idOf: r => r.external_id ?? r.id })`. O caminho de mock (`:132`) não muda.
- `musician-leads.ts:111`: `mapRowsLenient(rawRows, (r) => musicianLeadRowSchema.parse(r), { table: 'musician_leads', idOf: r => typeof r.id === 'string' ? r.id : undefined })`, com `rawRows` tipado como `readonly Record<string, unknown>[]`. Cursor a partir da última linha crua **já validada**: se a última crua for inválida, usar a última válida. Se nenhuma for válida e a página veio cheia, `nextCursor = null` e um `reportException` extra com fingerprint `['zod-schema-drift', 'musician_leads', 'page-unrecoverable']`. É o único caso em que o cursor de leads não pode ser montado sem os campos da linha.

- [ ] **Step 1: Testes** de `schema-drift.test.ts`: 3 linhas com a do meio inválida → 2 itens e `reportException` com `fingerprint: ['zod-schema-drift','events','starts_at']` e `recordId: 'ext-2'`; 5 inválidas → `[]` e 3 reportes; mapper lançando `TypeError` → rejeita com o mesmo `TypeError`; issue em `menu_items[2].price` → `issuePath === 'menu_items.*.price'`.
- [ ] **Step 2: Testes de service:** `listEvents` com `limit = 2`, mock retornando 2 linhas e a última inválida → `items.length === 1` e `nextCursor` codificando `starts_at`/`id` da **segunda** linha crua. `listNearbyEstablishments` com 1 linha inválida em 3 → 2 itens, sem lançar. `listMusicianLeads` com página cheia e a última inválida → cursor a partir da penúltima.

### Task 2: Services fora do padrão e fila de favoritos com teto

**Files:**
- Modify: `packages/core/src/services/favorites.ts:33-116` (4 funções), `packages/core/src/services/storage.ts:71-115` (`uploadImage`, `deleteImage`), `packages/core/src/services/metrics.ts:70-129` (`listOwnedMetrics`, `getOwnedFavoritesCountByEstablishment`) — envolver em `try { … } catch (error) { return handleServiceError(error, { method: 'favorites.addServerFavorite' }) }` etc. `args` só com `target.type`/contagem. Sem `userId` e sem `target.id`, porque o favorito liga pessoa a lugar.
- Modify: `packages/core/src/stores/useFavoritesStore.ts:13-16,66-82`
- Create: `isPermanentWriteError` em `packages/core/src/utils/error-classify.ts` (arquivo de 2.1)
- Test: `favorites.test.ts`, `storage.test.ts`, `metrics.test.ts`, `packages/core/src/stores/useFavoritesStore.test.ts` (criar se não existir), `error-classify.test.ts`

**Interfaces:**
- Produces:
  - `PendingOp` ganha `attempts?: number`. Campo opcional, então o estado persistido antigo continua válido e não precisa de migração. `CACHE_BUSTER` não muda: é do cache do TanStack, não desta store.
  - `export const MAX_PENDING_OP_ATTEMPTS = 5;`
  - `export function isPermanentWriteError(error: unknown): boolean` — Postgrest com `code` em `['42501', '23503', '23505', '23514', '22P02', 'PGRST301']`.
- `flushQueue`: no `catch(error)`, se `isPermanentWriteError(error)` ou `(pending.attempts ?? 0) + 1 >= MAX_PENDING_OP_ATTEMPTS`, descarta e chama `reportException(error, { method: 'favorites.flushQueue', fingerprint: ['favorites-queue-dropped', pending.op] })`. Senão, re-enfileira com `attempts + 1`. O `handleServiceError` dentro do service já terá reportado o erro original; o `WeakSet` de 2.1 dedup o segundo reporte do **mesmo** objeto. Por isso o drop reporta um `Error` novo, `new Error('FavoritesQueueDropped')`, com a fingerprint acima, e não o original.

- [ ] **Step 1: Testes:** cada service alterado, ao receber `{ error: postgrest42501 }`, rejeita com o mesmo objeto e chama `handleServiceError` (spy) com o `method` esperado e sem `userId` em `args`. Store: op com erro `42501` sai da fila em 1 flush; erro de rede permanece com `attempts === 1`; op com `attempts: 4` + erro de rede sai da fila; op que dá certo sai da fila; ops novas adicionadas durante o flush continuam (comportamento atual preservado).
- [ ] **Step 2:** FAIL → implementar → PASS.
- [ ] **Step 3: Commit** `Stop favorites queue from retrying forever` + CHANGELOG core ("Favoritos salvos offline não ficam mais presos tentando sincronizar").
