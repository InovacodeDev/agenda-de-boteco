Guia de Variáveis de Ambiente — Agenda de Boteco

Recriar do zero todas as variáveis de ambiente e segredos: Supabase, PostHog, Cloudflare R2, OTA, Vercel, EAS e GitHub Actions. Versão de 2026-11-09 (PR #115).

ATENÇÃO — segredos Nunca cole chave, token ou senha em arquivo do repo, em .env.example, em issue ou em chat. Valores reais vivem só no gerenciador de senhas, nos painéis (Supabase, PostHog, Cloudflare, Vercel, EAS, GitHub) e no seu terminal durante a configuração. A SUPABASE_SERVICE_ROLE_KEY nunca entra em app cliente (Vercel ou EAS).
Sobre os botões de copiar Os botões funcionam na versão HTML deste guia (docs/setup/guia-variaveis-ambiente.html). No PDF, selecione o texto do bloco e copie.
Ordem de execução
  1. Preparar ferramentas e o terminal
  2. Coletar valores nas origens (Supabase, PostHog, R2, Google, Expo, Apple)
  3. Gerar o par de chaves de assinatura do OTA
  4. Carregar os valores no terminal
  5. Supabase — segredos das Edge Functions
  6. GitHub Actions — secrets e variables
  7. Vercel — 5 projetos web
  8. EAS — 2 apps mobile
  9. Desenvolvimento local (.env.local)
  10. Verificar tudo
  11. Provisionar o PostHog (script)
  12. Apêndice — inventário completo

1. Preparar ferramentas e o terminal

  1. Confirme que as CLIs estão instaladas (todas já existem nesta máquina):
gh --version && eas --version && supabase --version && vercel --version
  1. Faça login em cada uma:
gh auth login
eas login
supabase login
vercel login
  1. Abra um terminal novo só para esta configuração e desligue o histórico dele, para que nenhuma chave fique salva em ~/.zsh_history:
unset HISTFILE
cd ~/git/agenda-de-boteco
CUIDADOUse sempre este mesmo terminal até o fim do passo 10. Ao fechar, as variáveis carregadas somem.

2. Coletar valores nas origens

Anote cada valor no gerenciador de senhas. Os nomes da coluna "Variável no terminal" são usados no passo 4.

2.1 Supabase (projeto de produção)

  1. Abra https://supabase.com/dashboard e selecione o projeto.
  2. Project Settings → General: copie o Reference ID.
  3. Project Settings → Data API (ou API): copie a Project URL.
  4. Project Settings → API Keys: copie a chave anon / public (ou a publishable). Copie também a service_role (ou secret).
  5. Project Settings → Database: anote a senha do banco. Se não souber, clique em Reset database password.
  6. Account → Access Tokens (https://supabase.com/dashboard/account/tokens): crie um token chamado github-actions-deploy.

  2. Confirme a região. US: https://us.i.posthog.com (ingestão) e https://us.posthog.com (API). UE: troque us por eu.

2.3 Cloudflare R2 (bucket do OTA)

  1. Em https://dash.cloudflare.com, copie o Account ID (barra lateral da conta). Variável: R2_ACCOUNT.
  2. R2 → Create bucket: nome agenda-ota. Se já existir, mantenha.
  3. No bucket: Settings → Public access. Conecte um domínio próprio (recomendado) ou habilite a URL r2.dev. Copie a URL pública, sem barra no fim. Variável: R2_PUBLIC_URL.
  4. R2 → Manage API tokens → Create API token: permissão Object Read & Write, restrita ao bucket agenda-ota. Copie o Access Key ID (R2_KEY_ID) e o Secret Access Key (R2_SECRET SECRET).

2.4 Google Maps (só app mobile do consumidor)

  1. Em https://console.cloud.google.com: APIs & Services → Credentials → Create credentials → API key.
  2. Crie uma chave para iOS (restrição: iOS apps, bundle do app) e uma para Android (restrição: Android apps, pacote + SHA-1 do certificado de upload).
  3. Habilite Maps SDK for iOS e Maps SDK for Android.
  4. Variáveis: GMAPS_IOS e GMAPS_ANDROID.

2.5 Expo / EAS

  1. Em https://expo.dev: Account settings → Access tokens → Create token, nome github-actions. Variável: EXPO_TOKEN_VALUE SECRET.
  2. Os IDs de projeto EAS já ficam fixos no código: apps/mobile/app.config.ts (14d06c33-…) e apps/mobile-client/app.config.ts (05db6b05-…). Se um projeto EAS for recriado, troque o extra.eas.projectId no arquivo e commite.

2.6 App Store Connect

  1. Em https://appstoreconnect.apple.com → Apps: abra cada app → App Information → copie o Apple ID numérico.
  2. Variáveis: ASC_ID_CONSUMIDOR (app consumidor) e ASC_ID_DONO (app do dono do bar).

3. Gerar o par de chaves de assinatura do OTA

ATENÇÃO — chave nova invalida os binários instalados O certificate.pem fica embutido no binário dos apps. Com uma chave nova, os apps já instalados rejeitam os próximos updates OTA, e é preciso um build nativo novo em todos os canais. Se a chave antiga estiver no gerenciador de senhas, pule este passo e use OTA_KEY_FILE apontando para ela.
  1. Gere o par fora do repo:
mkdir -p ~/agenda-ota-keys && cd apps/mobile
npx expo-updates codesigning:generate \
  --key-output-directory ~/agenda-ota-keys \
  --certificate-output-directory ./certs \
  --certificate-validity-duration-years 10 \
  --certificate-common-name "Agenda de Boteco"
cp ./certs/certificate.pem ../mobile-client/certs/certificate.pem
cd ../..
  1. Guarde ~/agenda-ota-keys/private-key.pem no gerenciador de senhas e apague a pasta no fim do passo 10.
  2. Commite os dois certificate.pem novos (é chave pública, pode ir para o git):
git add apps/mobile/certs/certificate.pem apps/mobile-client/certs/certificate.pem
git commit -m "Rotate OTA code signing certificate"

5. Supabase — segredos das Edge Functions

As funções ota-manifest e send-push leem SUPABASE_URL e SUPABASE_SERVICE_ROLE_KEY, que o Supabase injeta sozinho. Cadastre só os 2 segredos do OTA:

supabase secrets set --project-ref "$SB_REF" \
  OTA_PUBLIC_BASE_URL="$R2_PUBLIC_URL" \
  OTA_PRIVATE_KEY="$(cat "$OTA_KEY_FILE")"

Publique as funções, se o projeto for novo:

supabase link --project-ref "$SB_REF"
supabase functions deploy ota-manifest --project-ref "$SB_REF"
supabase functions deploy send-push --project-ref "$SB_REF"

8. EAS — 2 apps mobile

Cada app tem 3 environments: development, preview (canais alfa e beta) e production (lojas). Visibilidade: plaintext para EXPO_PUBLIC_*, que é embutida no app; sensitive para chaves de mapa; secret para chave de upload.

Primeiro, defina a função auxiliar (só existe neste terminal):

easenv() { # uso: easenv <visibilidade> <NOME> <valor> <environments...>
  local vis="$1" name="$2" value="$3"; shift 3
  for env in "$@"; do
    eas env:create --environment "$env" --name "$name" --value "$value" \
      --visibility "$vis" --non-interactive --force >/dev/null \
      && echo "ok  $name ($env)" || echo "ERRO $name ($env)"
  done
}

O script cria, em cada projeto: 9 insights, o dashboard [Agenda] Saúde de erros, 5 alertas, os destinos de Error Tracking (opcionais) e o Session Replay. Ele é idempotente. Rode primeiro em dry-run.

export POSTHOG_HOST="https://us.posthog.com"
# opcional: export POSTHOG_ALERT_WEBHOOK_URL="https://hooks.slack.com/..."
# opcional: export POSTHOG_ALERT_USER_EMAILS="voce@inovacode.dev"

for id in 591092 591110 591111 591113 591114; do POSTHOG_PROJECT_ID=$id pnpm posthog:setup; done

for id in 591092 591110 591111 591113 591114; do POSTHOG_PROJECT_ID=$id pnpm posthog:setup --apply; done
unset POSTHOG_PERSONAL_API_KEY POSTHOG_ALERT_WEBHOOK_URL POSTHOG_ALERT_USER_EMAILS

12.3 Fora de variáveis de ambiente, mas necessário num projeto do zero

  • Supabase Auth (painel → Authentication): provedores Google e Apple (client ID e secret), URLs de redirect (/client/login, /app/..., schemes agenda-de-boteco:// e agenda-boteco-client://), SMTP e templates de e-mail (supabase/emails/).

  • Cloudflare R2: lifecycle do bucket com node scripts/ota/setup-r2-lifecycle.mjs (usa as mesmas R2_*).
  • EAS: credenciais de assinatura (passo 8.3) e conta de serviço do Google Play para submit.
